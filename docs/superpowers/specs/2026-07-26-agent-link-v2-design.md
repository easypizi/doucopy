# agent-link v2: открытый self-host, простой сетап, параллельные диалоги

Дата: 2026-07-26
Статус: дизайн утверждён, ожидает ревью перед планом имплементации
Базируется на: `2026-07-23-agent-link-design.md` (v1, реализован полностью)

## 1. Цель и контекст

v1 работает для пары своих машин, но требует семи ручных шагов на подключение и ручной регистрации каждого токена оператором релея. v2 превращает agent-link в open-source проект, который любая группа (команда, компания, круг знакомых) разворачивает для себя:

- Подключение новой машины одной командой, без участия оператора релея.
- Идентификатор участника - произвольное имя, которое он сам выбирает. Email и другие внешние идентификаторы не используются.
- Одна машина ведёт несколько парных диалогов параллельно.
- CLI-команда показывает состояние подключений и диалогов с обеих ролей (спрашивающий и отвечающий).

Модель хостинга: каждая группа деплоит свой релей. Центрального сервиса нет.

Диалоги остаются парными (peer-to-peer). Групповые комнаты и широковещательные вопросы в v2 не входят.

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Аудитория | Open-source, self-hosted круги |
| Хранение участников | Stateless HMAC-токены, без базы данных |
| Идентификатор | Произвольное имя, выбранное пользователем |
| Допуск | Инвайт-коды, которые генерирует любой участник |
| Интерфейс наблюдения | CLI (`agent-link status`), без веб-дашборда |
| Диалоги | Парные, до 3 параллельных обработок на демоне |
| Свои MCP у пользователей | Не нужны, MCP-сервер живёт на релее группы |
| ОС | macOS (launchd), Linux вне скоупа v2 |

## 3. Идентичность и доступ (stateless)

Единственное состояние авторизации на релее - config var `RELAY_SECRET` (случайные 32+ байта). Переменные `PEER_TOKEN_*` уходят полностью.

### 3.1. Формат токенов

Токен участника (выдаётся релеем при вступлении):

```
al1.<base64url(name)>.<base64url(HMAC-SHA256(secret, "peer:" + name))>
```

Релей проверяет подпись и достаёт имя из самого токена. Реестр участников не хранится нигде.

Инвайт-код (выдаётся релеем по запросу участника):

```
ali1.<expiry_unix>.<nonce>.<base64url(HMAC-SHA256(secret, "invite:" + expiry_unix + ":" + nonce))>
```

`nonce` - случайные 8 байт, чтобы коды были различимы. Срок жизни по умолчанию 72 часа. Инвайт многоразовый до истечения срока: без хранилища одноразовость невозможна, для закрытого круга это принятый компромисс.

### 3.2. Новые REST-эндпоинты релея

- `POST /join` с телом `{invite, name}`, без авторизации. Релей проверяет подпись и срок инвайта, отклоняет имя, если пир с таким именем сейчас онлайн (poll в последние 60 секунд) или числится в отозванных, и возвращает `{token, peer: name}`.
- `POST /invite` с авторизацией, тело `{ttl_hours?}`. Возвращает `{invite, expires_at}`.
- `GET /status` с авторизацией. Срез состояния релея для вызывающего пира:

```json
{
  "self": "ivan-mbp",
  "peers": [{"name": "work", "online": true}],
  "incoming_queued": 2,
  "outgoing": [
    {"ticket_id": "…", "to_peer": "work", "status": "pending", "created_at": 1785…}
  ]
}
```

Для `outgoing` mailbox начинает хранить `to_peer` и `from_peer` в pending-записях (сейчас там только результат).

### 3.3. Отзыв доступа

Config var `REVOKED_PEERS` - список имён через запятую. Проверяется при каждой аутентификации и при `/join`. Смена `RELAY_SECRET` отзывает всех сразу.

### 3.4. Принятые компромиссы stateless-подхода

- `list_peers` и `/status` видят только пиров, поллинг которых релей наблюдал после последнего рестарта дины. Демоны поллят каждые 25 секунд, поэтому список восстанавливается почти мгновенно.
- Два участника теоретически могут получить одно имя (проверка коллизий работает только против онлайн-пиров). Внутри доверенного круга это не атака, а недоразумение, документируется.
- Инвайты многоразовые до истечения. Компенсация: короткий TTL по умолчанию.

## 4. Сетап одной командой

### 4.1. Публикация в npm

Репозиторий публикуется как один npm-пакет `agent-link` с bin `agent-link`. Внутренняя структура workspaces (relay, daemon) сохраняется для разработки, но сборка кладёт всё в один публикуемый артефакт с тремя точками входа: CLI, релей, демон.

### 4.2. Подключение машины

```bash
npx agent-link join <relay-url> <invite-код>
```

Команда интерактивно спрашивает имя участника и дальше делает всё сама:

1. `POST /join`, получает токен.
2. Пишет `~/.agent-link/config.json` (тот же формат, что в v1, секция 3.3 старой спеки) с правами 0600. Обнаружение источников памяти (transcripts glob, AGENTS.md roots) переносится из `setup-machine.sh`.
3. Создаёт стартовый `~/.agent-link/policy.md`, если его нет.
4. Собирает демона (если запущено из клона) или использует установленный пакет, ставит launchd-агент (логика текущего `install-daemon.sh`).
5. Добавляет запись `agent-link` в `~/.cursor/mcp.json` (мержит, не перезаписывает файл).
6. Проверяет: демон поллит, `list_peers` на релее показывает нового участника.

Скрипты `setup-machine.sh` и ручная регистрация токенов на Heroku удаляются. `install-daemon.sh` становится внутренней функцией CLI.

### 4.3. Деплой релея

- Heroku: файл `app.json` в корне репозитория с `RELAY_SECRET` типа `generator: secret` и кнопка "Deploy to Heroku" в README. Один клик, ноль ручных env-переменных.
- Без Heroku: `RELAY_SECRET=… npx agent-link relay` поднимает релей на любой машине с Node, плюс Dockerfile для контейнерного запуска.

## 5. Параллельные диалоги

В v1 демон обрабатывает вопросы строго последовательно: `pollOnce` ждёт завершения обработчика. В v2:

- Получив вопрос, демон отдаёт его в асинхронную обработку и сразу возвращается к поллингу.
- Лимит одновременных обработок: 3, поле конфига `responder.max_concurrent`. При достижении лимита поллинг приостанавливается до освобождения слота.
- У каждого диалога свой рабочий каталог: `~/.agent-link/workspace/<conversation_id>/task.md`. Общий `task.md` уходит, иначе параллельные запуски `cursor-agent` затирают задания друг друга.
- Каталоги диалогов старше 7 дней вычищаются при старте демона, синхронно с прунингом `conversations.json`.
- Редакция секретов и policy применяются к каждому ответу независимо, как в v1.

## 6. CLI-интерфейс

Команды bin `agent-link`:

- `join <relay-url> <invite>` - подключение машины (секция 4.2).
- `invite [--ttl <часы>]` - получить инвайт-код с релея и напечатать готовую команду для новичка.
- `status` - сводка текстом: локальный демон (запущен ли, uptime, последняя ошибка из лога), пиры с `GET /status` (имя, онлайн), очередь входящих, мои исходящие тикеты со статусами.
- `start`, `stop`, `restart` - управление launchd-агентом (обёртки над launchctl, логика текущего `daemon.sh`).
- `logs [-f]` - хвост `~/.agent-link/responder.log`.
- `relay` - запустить релей локально (секция 4.3).

`status` работает и когда демон остановлен: локальная часть покажет "остановлен", релейная часть отработает по токену из конфига.

## 7. Что не меняется

MCP-инструменты (`list_peers`, `ask_peer`, `check_reply`) и их семантика, mailbox с TTL и overflow, long-poll и keepalive-пинги, промпты респондера, `conversations.json` c `--resume`, редакция секретов (`redact.ts`), механика launchd. Скиллы в `.cursor/skills/` обновляются под новые команды, но их состав сохраняется.

## 8. Безопасность

- HMAC-SHA256 с общим секретом релея, сравнение подписей постоянного времени (как в v1 для хешей токенов).
- Токен содержит имя открытым текстом (base64url), это не секретная часть. Секретна подпись.
- `RELAY_SECRET` знает только релей. Участники не могут выпускать токены сами, только через `/join` с валидным инвайтом.
- `POST /join` без авторизации - точка перебора. Защита: rate limit (например, 10 запросов в минуту на IP) и проверка подписи инвайта до любых действий.
- Остальное наследуется из v1: TLS, права 0600 на конфиг, policy.md на отвечающей стороне, жёсткая редакция секретов в коде демона.

## 9. Совместимость и миграция

Ломающее изменение: старые `PEER_TOKEN_*` токены перестают работать. Миграции нет, существующие машины (personal, work) переподключаются через `npx agent-link join` после деплоя v2. Существующий Heroku-инстанс получает `RELAY_SECRET` и теряет `PEER_TOKEN_*` в одном действии.

## 10. Тестирование

- Юнит-тесты auth: выпуск и проверка peer-токенов и инвайтов, истёкший инвайт, порченая подпись, отозванное имя, коллизия с онлайн-пиром.
- Юнит-тесты `/join`, `/invite`, `/status` через `app.inject`, как существующие REST-тесты.
- Тесты параллельности демона: два вопроса разных диалогов обрабатываются одновременно (заглушка cursor-agent с задержкой), третий ждёт слота при лимите 2, каждый пишет в свой каталог.
- Тесты CLI: `join` против локально поднятого релея в temp-окружении (HOME подменяется), проверка записанных config.json и mcp.json.
- Интеграционный тест v1 (полный цикл MCP - демон - ответ) адаптируется под новую auth и остаётся.
- Ручной e2e: деплой на существующий Heroku-инстанс, переподключение обеих машин через новый flow, `agent-link status` с обеих, параллельный вопрос двум диалогам.

## 11. Что не входит в v2 (YAGNI)

- Групповые комнаты и широковещательные вопросы.
- Веб-дашборд.
- База данных на релее, персистентность очередей между рестартами дины.
- Одноразовые инвайты и точный реестр участников.
- Email и любая внешняя верификация личности.
- Linux (systemd) и Windows. Структура CLI закладывается так, чтобы платформенная часть (launchd) была отделена, но реализация только macOS.
- Ротация `RELAY_SECRET` без полного переподключения участников.

## 12. Открытые вопросы к моменту имплементации

- Точная схема сборки одного npm-пакета из двух workspaces (bundling против публикации трёх пакетов). Решается на первом шаге плана.
- Библиотека для CLI: голый `parseArgs` из node:util против commander. Склоняемся к `parseArgs`, ноль зависимостей.
- Rate limit на `/join`: встроенными средствами Fastify (`@fastify/rate-limit`) или простым in-memory счётчиком. Решается при имплементации.
